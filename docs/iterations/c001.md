## Mechanism and alternatives

The C++ runtime owns requests, frame advancement, merged predictor/talker graph
replay, codec graph replay, compaction and PCM conversion. The `qtts` executable
uses a C API to advance the core. Python loads weights, tokenizes, prefills and
captures graphs; HTTP reuses the pinned upstream protocol adapter. The native
runtime does not execute `ContinuousModel.tick`.

Options considered:

- A C++ launcher around the original Python loop would retain per-frame Python
  ownership and would not meet the implementation goal; rejected.
- A completely Python-free loader, tokenizer, prefill and server would greatly
  expand the first change; deferred. This implementation states its boundary.
- Linking libtorch/CANN directly into the executable caused `aclInit 500000`
  during development. Loading the extension after normal Python initialization
  and then calling its C API completed successfully; failed logs are retained.
- Existing optimized native predictor rotary is retained in C001. Operator
  replacement is a subsequent, separately qualified iteration.
