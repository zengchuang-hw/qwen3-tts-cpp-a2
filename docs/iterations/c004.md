# C004: inline audio delivery

Prior design: [RFC #8](https://github.com/zengchuang-hw/qwen3-tts-cpp-a2/issues/8).
Hypothesis: the old core waits for all codec groups before exposing any PCM,
while reference emits group by group. Removing this batch-local wait may improve
high-concurrency TTFA without changing speech math, chunk sizes or scheduling.

The native runtime accepts an optional synchronous audio callback after each
codec group's PCM is ready. Pybind releases the GIL for execution and reacquires
it only for Python emission. Completion events still return after state handling.
The core has a single owning thread; callbacks may observe state, but mutation
or step reentry is rejected. An exception aborts the step, resets the guard and
permits cleanup; partially emitted requests are never counted as successes.

Select `--audio-delivery inline` in `serve.py`, `probe.py` or `campaign.py`.
Default `buffered` remains the control. The C API ABI and complete-WAV C++ CLI
keep their existing behavior; no CLI streaming-latency improvement is claimed.
`probe.py --verify-inline` witnesses the actual call boundary and rejects reentry;
`--fail-emit` validates intentional exception propagation/cleanup only.

`campaign.py --reference-engine native-buffered` is an explicit causal control
using the same candidate code with buffered delivery. It cannot establish an
upstream performance PASS, even with full repetitions/cohorts. The default
upstream comparison and its frozen seven-concurrency gates remain unchanged.
Neither a local callback witness nor a reduced pilot establishes whole-target
performance. All attempts, regressions and scope limitations must be retained.

Required A2 validation and the bounded pilot are specified in RFC #8. Results
will be retained under `evidence/c004-inline-audio/` and in the PR review comment.
No new performance or quality PASS is asserted before those results exist.
